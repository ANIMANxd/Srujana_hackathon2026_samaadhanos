## Blocker

### B1 — The frontend does not typecheck: `BAND_TONE` is missing `EVIDENCE_COMPLETE`
- `frontend/components/pack/PackScreen.tsx:18` declares
  `const BAND_TONE: Record<ReadinessBand, Tone> = { COURT_READY, ACTION_NEEDED, BLOCKED }`
  — three keys, while the contract union has four:
  `contracts/types.ts:760` (and its synced copy `frontend/generated/contract-types.ts:761`)
  `ReadinessBand: "COURT_READY" | "EVIDENCE_COMPLETE" | "ACTION_NEEDED" | "BLOCKED"`.
  A `Record` over the union needs every member, so `tsc` fails (missing-key
  error) and `npm run typecheck` / `npm run build` fail with it.
- Runtime as well: `PackScreen.tsx:74` indexes `BAND_TONE[band]`, which is
  `undefined` for an `EVIDENCE_COMPLETE` band (the band the engine now emits —
  CQ-23), so the status icon would lose its tone.
- Statically proven (union read from the generated file); `tsc` deliberately
  not run, per this role's read-only boundary.
- **What would settle it:** CR-3 in `frontend/CONTRACT-REQUESTS.md` — the
  rename `COURT_READY → EVIDENCE_COMPLETE` needs both humans (architecture
  section 9.3), and then the frontend owner adds the key (the i18n string
  already exists: `frontend/lib/i18n/en.ts:241-242`).

### B2 — The gate can exclude a *small* supplier, reported as `EXCLUDED_MEDIUM`
- `backend/engine/gate.py:294` looks up `limits = getattr(epoch, stated.lower(), None)`
  — the ceilings of the **class the request states** — and `gate.py:333-338`
  then measures the *figures* against those ceilings. A request that states
  `enterprise_class: MICRO` with investment 24 crore (inside the configured
  small ceilings of 25/100) fails on "investment 24 crore exceeds 2.5 crore"
  and the case is reported `EXCLUDED_MEDIUM`.
- That contradicts architecture section 6.1: the class is *"looked up in
  `size_epochs`"* on the supply date and *"Medium and above fail"*; 24 crore is
  small, not medium, and reverse graduation (the concept the check's own detail
  text invokes) only means anything if the figures decide the class. The status
  name also contradicts the figures it was measured against.
- Evidence: spec test `backend/tests/spec/test_s4_gate_blocks.py::test_a_supplier_inside_the_ceiling_is_not_excluded_as_medium`
  (failing, recorded as finding F2 in `docs/test-oracles.md`), plus API probes:
  the same figures pass when the request states `SMALL`, and 9 crore fails when
  it states `MICRO` — the stated class, not the figures, decides.
- **What would settle it:** the V6 capture (the real investment/turnover
  limits by date) and a ruling in architecture 6.1 on stated-class validation
  vs figures-derived classification.

## Major

### M1 — A payment on a rest date that is also the calculation date is dropped
- `backend/engine/interest.py:518-521` collects pending payments (inclusive of
  the calculation date), the walk runs `while anchor < calculation_date`
  (`interest.py:529`), and on a rest the handler `continue`s
  (`interest.py:568-571`). When the rest date **is** the calculation date, the
  loop exits after capitalising and the pending payment is never applied: in
  the repro, principal stays `365000.00` and interest outstanding `5115.00`
  instead of `270115.00 / 0.00` — the claim is overstated by the whole payment.
- The code's own comment at `interest.py:537-538` says a payment on a rest date
  is "capitalised before it is applied", and with the calculation date one day
  later the same payment *is* applied — so only the triple collision
  (payment = rest = calculation date) fails.
- Evidence: spec test `test_s3_interest_ledger.py::test_payment_on_the_rest_day_that_is_also_the_calculation_date`
  (finding F1); the passing sibling test pins the correct behaviour.
- **What would settle it:** architecture 6.3 (accrue to the payment date,
  capitalise, apply, restart from there) with OQ-3's convention; no statute
  needed.

### M2 — The Silpi block is unreachable, so judge rehearsal #5 does nothing
- `backend/engine/gate.py:370-374`: `_check_silpi_chronology(config, contract_date, supply_date)`
  never receives the Udyam registration date, and when the configured anchor
  exists it returns `passed=True` unconditionally (`gate.py:441-449`) — the
  comment at `gate.py:433-435` concedes it "only records that the chronology
  could be fixed". `BARRED_SILPI` therefore never fires.
- Architecture 6.1 names this check `silpi_chronology` and section 11 lists
  "Silpi blocks" (and rehearsal #5, "flip the Udyam date past the Silpi test
  date") as required edges; today the edit produces no change at all.
- Evidence: spec finding F3 (`docs/test-oracles.md`) and contract test
  `test_judge_manipulations.py::TestJudgeManipulations::test_judge_5_flip_the_udyam_date_past_the_silpi_test_date`
  (both fail); probes show `passed=True` for registration before *and* after
  the anchor, under both `SUPPLY` and `CONTRACT`.
- **What would settle it:** the V4 capture — the works-contract/Silpi rule,
  its direction and its anchor. OQ-2 currently asks only which date anchors the
  test, not what is compared with what.

### M3 — Duplicate payments are accepted and double-counted
- The request schema has no uniqueness rule (`backend/app/schemas.py`,
  `PartPayment`) and the engine applies both rows: two identical
  `2026-06-10 / 50000.00` entries take principal from `365000.00` to
  `265000.00`, and the ledger books `50000.00` twice
  (`backend/engine/interest.py:518+`).
- Evidence: spec finding F4, `test_malformed_inputs.py::test_duplicate_payments_are_refused`
  (expected 400/422 per the suite brief; actual 200).
- **What would settle it:** a product rule for identical date+amount+reference
  rows (one payment or two), then schema validation under section 8.1. No
  statute is involved; the harm is a wrong claim figure.

### M4 — A negative credit period is accepted, putting the due date before delivery
- `Transaction.written_credit_days` (`backend/app/schemas.py`) accepts `-20`;
  the engine applies it as agreed: `applied_days = -20`, **due 2026-05-12 for
  a 2026-06-01 delivery**, appointed 2026-05-13, `days_overdue = 46`.
  Delay, interest days and any limitation anchor downstream are then computed
  from a due date that precedes the goods.
- Evidence: spec finding F5,
  `test_malformed_inputs.py::test_other_impossible_values_are_refused`.
- **What would settle it:** architecture 6.2 (due = acceptance + applied days,
  and acceptance cannot precede delivery) plus the V2 capture for the allowed
  range of an agreed credit period; the fix is a schema constraint.

## Minor

### m1 — A calculation date before delivery is answered 200, not a refusal
`test_malformed_inputs.py::test_calculation_date_before_delivery_is_refused`
(finding F6). The engine degrades safely — empty ledger, `days_overdue: null`,
claim = principal, `NO_DELAY_PRICED` warning — so nothing nonsensical is
computed, but section 8.1 says rule violations get 400 and the input is
incoherent. *Settled by:* a decision in the error model — warning (current) vs
rule violation.

### m2 — `late_complaints` mirrors the request's array order
`backend/engine/acceptance.py:250` appends in input order and never sorts, so
the same objections listed differently give different response objects (all
computed values identical). Spec invariant test
`test_invariants.py::test_shuffling_objections_does_not_change_the_output`
(finding F7). *Settled by:* a line in architecture 6.2 — sort by date, or
document the order as input order.

### m3 — `openapi.json` mis-declares the error responses (CQ-48)
Every 422 declares FastAPI's `HTTPValidationError` (e.g.
`paths./api/v1/evaluate-case.post.responses.422`), `/presets/{id}` declares no
404 although it returns one, and `health`/`config`/`presets` 200s are free-form
objects — while the app returns section 8.1's `{error: {code, message, field?}}`.
A consumer validating errors against the document would be wrong.
Runtime behaviour is pinned by
`backend/tests/contract/test_openapi_conformance.py::test_error_responses_use_the_contract_envelope`.
*Settled by:* attaching `responses={...}` models to the routes and re-exporting
— a section 9 contract change, deliberately not slipped in by a test.

### m4 — The `years_deferred` default's value exists only in code
`backend/engine/evaluate.py:64` `DEFAULT_YEARS_DEFERRED = Decimal("1.00")`.
Architecture 6.4 says the inputs "have UI defaults" without giving the value,
so this constant has no documented value. It is **not** silent — the applied
default is announced in `assumptions[]` (`evaluate.py:207-211`, citing 6.4
correctly). *Settled by:* stating 1.00 in architecture 6.4 (or moving it into
the statute config as a non-statutory input default).

### m5 — Extraction's window rule has no `citations[]` slot
The lateness tag applies the configured `objection_window_days`, and the
response carries the source ref and verified flag **inside a warning**
(`backend/extraction/extract.py`, `OBJECTION_WINDOW_APPLIED`), but
`ExtractionResponse` (`backend/app/schemas.py`) has no `citations[]` like
every engine block does. Golden rule "every result that depends on a rule
includes citations[]" is met in spirit, not in shape. *Settled by:* adding
`citations[]` to `ExtractionResponse` (section 9, additive) or documenting the
warning as the citation carrier for extraction.

### m6 — Demo inputs are duplicated (CR-7 open)
`frontend/demo-cases/demo_02.request.json` and `demo_03.request.json` still
ship alongside the real `backend/presets/case_02/case_03` — two hand-maintained
copies of the same synthetic inputs, which can drift (golden rule 7 hygiene;
both are labelled inputs, so nothing is misrepresented today). *Settled by:*
CR-7 — delete the demo files now the presets have landed.

### m7 — Offline fallback copy states statutory facts without a citation
`frontend/lib/i18n/en.ts:306-311` (`tpl.1`–`tpl.3`) says "Under the MSMED
Act, interest ... compounding monthly, and is not tax-deductible" in the
fallback draft. Mitigated: it only renders behind the `send.placeholder_draft`
banner (`SendScreen.tsx:150`) and the rate still comes from the engine's
segment, but the sentence itself carries no source. *Settled by:* copy review —
either attribute it or phrase it as the app's own calculation.
